## 3. 与 spec 的偏差：未引入 riverpod_generator

### 3.1 探索过程

第一次按 spec 写 `riverpod_annotation: ^2.6.0` + `riverpod_generator: ^2.6.0` → pub 解析失败：

```
riverpod_generator <3.0.0-dev.17 depends on build ^2.0.0
freezed 3.x + retrofit_generator 10.x 需要 build 3.x+
→ riverpod_generator 2.x 与现有 codegen 链不兼容
```

升级到 `^3.0.0-dev.17` / `^3.0.0` → 另一冲突：

```
riverpod_generator 3.x depends on analyzer 7.x-9.x
json_serializable 6.13+ depends on analyzer 10.x+
→ analyzer 版本不兼容
```

### 3.2 决策：放弃 codegen，手写 Provider

权衡：
- **强行解决**：降级 json_serializable 至 ≤6.12 → 拉低整个项目分析器版本，影响 freezed / retrofit
- **接受偏差**：仅引入运行时 `flutter_riverpod`，手写 Provider 声明（功能 100% 等价，只是不省样板）

选择第二条。手写 Provider 在 Riverpod 社区仍是主流（很多团队拒绝 codegen 以避开 build_runner 复杂性）。等 riverpod 3.x + 整条 codegen 链对齐后再回写 codegen。

### 3.3 手写 vs codegen 对照

```dart
// codegen 写法（@riverpod）：
@riverpod
String greeting(Ref ref) => 'Hello';

// 手写写法（T06.1/T06.2 采用）：
final greetingProvider = Provider<String>(
  (ref) => 'Hello',
  name: 'greetingProvider',
);
```

行为完全一致，可读性接近。手写的额外好处：`name:` 参数可显式（codegen 会从函数名推导）。

## 4. main.dart 接入

```dart
void main() {
  runApp(
    ProviderScope(
      observers: <ProviderObserver>[AppProviderObserver()],
      child: const MyApp(),
    ),
  );
}
```

注：现阶段 main.dart 不调 `configureDependencies()`（M13/T13.1 重写时统一接管）。AppProviderObserver 在 main 中直接 `new`；DI 注册（`@lazySingleton`）保留，便于 M13 之后通过 `getIt<AppProviderObserver>()` 拿同一实例。
