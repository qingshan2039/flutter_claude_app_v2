## 4. 源码设计

### 4.1 `lib/core/di/injection.dart`（DI 主入口，本任务核心交付物）

```dart
import 'package:get_it/get_it.dart';
import 'package:injectable/injectable.dart';

import 'injection.config.dart';

final GetIt getIt = GetIt.instance;

@InjectableInit()
Future<GetIt> configureDependencies({String? environment}) async {
  return getIt.init(environment: environment);
}
```

设计要点：

- `getIt`：全局唯一 `GetIt.instance`，所有依赖注册到此实例
- `configureDependencies({String? environment})`：异步函数，封装 `getIt.init()`。`environment` 参数（dev / staging / prod）支撑 T02.3 「按环境注册不同实现」与 M15 多环境配置
- `@InjectableInit()`：注解触发代码生成。所有默认参数：`initializerName='init'`、`asExtension=true`，使生成的方法为 `extension GetItInjectableX on GetIt { GetIt init(...) }`

### 4.2 `lib/core/utils/app_info.dart`（最小示例服务）

```dart
import 'package:injectable/injectable.dart';

@lazySingleton
class AppInfo {
  AppInfo();

  String get name => 'flutter_claude_app_v2';
  String get version => '1.0.0+1';
}
```

设计要点：

- T02.1 引入 **最小示例**：仅 1 个 `@lazySingleton` 服务，让 build_runner 有真实注解可生成代码，并支持端到端验证
- T02.3「DI 注册示例」会扩充至 Singleton / LazySingleton / Factory + 按环境注册的完整示范
- 选择 `AppInfo` 这个语义中性的服务（无平台依赖、无外部包），避免引入与 M02 无关的复杂度

### 4.3 `lib/core/di/injection.config.dart`（build_runner 生成）

由 `injectable_generator` 自动产出（**禁止手工修改**）：


## 7. 实施过程中遇到的问题与解决

T02.1 实施过程中遇到 2 个问题，均已解决并记录。

### 7.1 问题一：自定义 `initializerName` 与调用名不一致导致编译失败

- **现象**：首次写 `injection.dart` 时用了 `@InjectableInit(initializerName: r'$initGetIt')`，但函数体内仍调用 `getIt.init(...)`。生成的扩展方法名为 `$initGetIt`，与 `init` 不匹配，编译会报「undefined method `init`」
- **修复**：移除 `initializerName` 等自定义参数，回退到 `@InjectableInit()` 默认值（`initializerName='init'`、`asExtension=true`），与函数体内的 `getIt.init(...)` 调用对齐
- **教训**：对生成代码的自定义参数要么不动、要么所有引用同步改

### 7.2 问题二：未注册类型抛出的错误类型与预期不一致

- **现象**：第一版测试 `expect(() => getIt<AppInfo>(), throwsA(isA<AssertionError>()))` 失败。get_it 8.3.0 实际抛 `StateError`（"Object/factory with type AppInfo is not registered..."），不是 `AssertionError`
- **修复**：改为 `throwsStateError` matcher，与 get_it 8.x 实际行为对齐
- **教训**：测试 `expect(throwsA(...))` 时若不确定具体错误类型，先查包源码或先用宽松 matcher（`throwsA(isA<Error>())`）再收紧

## 8. 与 spec 的偏差与决策

T02.1 的实施与 spec 一致，没有版本号、范围等偏差。两个值得说明的设计决策：

### 8.1 决策一：T02.1 引入 1 个 `@lazySingleton` 示例服务

- **spec 期望**: T02.1 仅交付「DI 主入口 + 配置脚本」；示例放在 T02.3
- **实际**: T02.1 额外引入 `AppInfo` 一个最小示例
- **理由**: 用户附加要求「依赖注册 / 代码生成 / 运行调用 / 单元测试」需要至少 1 个实际可注册的类，否则 build_runner 仅产出空 `init()` 扩展，无法验证「运行调用」与「单元测试」。这 1 个示例不构成 T02.3 的「完整示例集」，只是验证链路所需的最小样本。
- **T02.3 仍会扩充**: Singleton / LazySingleton / Factory 三种注册 + 按环境注册 + 测试场景替换依赖

### 8.2 决策二：`AppInfo` 暂用硬编码，不引入 `package_info_plus`

- **理由**: T02.1 范围内不应引入额外依赖。`AppInfo.name / version` 后续在 M15（环境配置）/ M11（监控）中会替换为 `package_info_plus` 真实读取。
