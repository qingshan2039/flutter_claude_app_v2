## 3. 三种注册类型的语义差异

T02.3 通过 3 个示例 + 4 条测试演示三种注册模式的核心差异。

### 3.1 `@singleton`（eager 单例）

```dart
@singleton
class EagerSingletonService {
  EagerSingletonService() : initializedAt = DateTime.now();
  final DateTime initializedAt;
}
```

- **何时构造**：`configureDependencies()` 调用瞬间，**即使没人 `getIt<T>()`**
- **何时销毁**：`getIt.reset()` 时
- **适合场景**：启动即需可用的服务（EventBus、SessionManager、AnalyticsClient）；构造函数中执行启动副作用的服务
- **副作用提示**：在构造函数里调 IO 会拖慢启动；必要时改用 `@lazySingleton`

### 3.2 `@lazySingleton`（lazy 单例）

```dart
@lazySingleton
class AppInfo {
  AppInfo();
  String get name => 'flutter_claude_app_v2';
  String get version => '1.0.0+1';
}
```

- **何时构造**：第一次 `getIt<T>()` 时
- **何时销毁**：`getIt.reset()` 时
- **适合场景**：默认选择。除非有「启动即用」需求，否则用 lazy
- **优势**：启动更轻；从未被使用的服务不占内存

### 3.3 `@injectable`（factory）

```dart
@injectable
class FactoryService {
  FactoryService() : createdAt = DateTime.now();
  final DateTime createdAt;
}
```

- **何时构造**：每次 `getIt<T>()`
- **何时销毁**：调用方持有引用消失时（普通 GC）
- **适合场景**：请求级 ID 生成器、表单状态对象、UUID 生成器
- **陷阱**：若误用为「重共享状态」的服务，多次解析会拿到不同实例，导致状态丢失

### 3.4 三种类型的行为对照（来自生成代码）

[lib/core/di/injection.config.dart](file:///Users/ben/ai_project/flutter_claude_app_v2/lib/core/di/injection.config.dart) 第 32-36 行：

```dart
gh.factory<_i237.FactoryService>(() => _i237.FactoryService());           // @injectable
gh.singleton<_i591.EagerSingletonService>(                                // @singleton
  () => _i591.EagerSingletonService(),
);
gh.lazySingleton<_i642.AppInfo>(() => _i642.AppInfo());                   // @lazySingleton
```

GetItHelper 内部对三者的处理：
- `factory`：注册一个 builder，每次解析时调用一次 builder
- `singleton`：注册时即调用 builder 一次，结果缓存
- `lazySingleton`：注册 builder，第一次解析时调用并缓存

## 4. 按环境注册（`@dev` / `@prod`）

T02.3 的 [environment_aware_service.dart](file:///Users/ben/ai_project/flutter_claude_app_v2/lib/core/di/examples/environment_aware_service.dart) 展示了「同一接口、按环境提供不同实现」的标准模式。

### 4.1 接口与实现

```dart
abstract class ApiClient {
  Future<String> fetch();
  String get name;
}

@dev
@LazySingleton(as: ApiClient)
class MockApiClient implements ApiClient {
  @override String get name => 'MockApiClient';
  @override Future<String> fetch() async => 'mock-data';
}

@prod
@LazySingleton(as: ApiClient)
class RealApiClient implements ApiClient {
  @override String get name => 'RealApiClient';
  @override Future<String> fetch() async => 'real-data';
}
```

### 4.2 生成代码（关键片段）

```dart
const String _dev = 'dev';
const String _prod = 'prod';

extension GetItInjectableX on _i174.GetIt {
  _i174.GetIt init({String? environment, _i526.EnvironmentFilter? environmentFilter}) {
    final gh = _i526.GetItHelper(this, environment, environmentFilter);
    ...
    gh.lazySingleton<_i767.ApiClient>(
      () => _i767.MockApiClient(),
      registerFor: {_dev},
    );
    gh.lazySingleton<_i767.ApiClient>(
      () => _i767.RealApiClient(),
      registerFor: {_prod},
    );
  }
}
```

`registerFor: {_dev}` 让 GetIt 只在传入 `environment: 'dev'` 时执行此次注册。

### 4.3 运行时切换

```dart
// 开发期
await configureDependencies(environment: 'dev');
final client = getIt<ApiClient>();  // → MockApiClient

// 生产
await configureDependencies(environment: 'prod');
final client = getIt<ApiClient>();  // → RealApiClient

// 测试或忘传 environment
await configureDependencies();
getIt.isRegistered<ApiClient>();   // → false
```

### 4.4 与 M15 的衔接

`environment` 字段在 M15 / T15.3 完成后会从 `--dart-define ENV=...` 注入，例如：

```bash
flutter run --dart-define=ENV=dev    # 开发
flutter run --dart-define=ENV=prod   # 生产
```

入口 `main.dart` 会读 `String.fromEnvironment('ENV')` 传给 `configureDependencies`。

## 5. 测试场景：手动替换依赖

T02.3 的 [test_replacement_test.dart](file:///Users/ben/ai_project/flutter_claude_app_v2/test/core/di/test_replacement_test.dart) 演示 **4 种测试场景下的依赖替换模式**。

### 5.1 模式 A：configure 前手动注册（跳过 injectable）

```dart
await getIt.reset();
getIt.registerLazySingleton<ApiClient>(() => FakeApiClient('payload-A'));
// 不调用 configureDependencies()
final client = getIt<ApiClient>();   // → FakeApiClient
```

适合：测试只关心某一个依赖，不需要完整启动链。

### 5.2 模式 B：configure 后替换（unregister + 重新 register）

```dart
await getIt.reset();
await configureDependencies(environment: 'dev');   // 拿到 MockApiClient
await getIt.unregister<ApiClient>();
getIt.registerLazySingleton<ApiClient>(() => FakeApiClient('payload-B'));
```

适合：测试需要其他依赖已注册，但要 override 其中 1-2 个。

### 5.3 模式 C：用 fake 验证调用次数

```dart
final fake = FakeApiClient('counted');
getIt.registerSingleton<ApiClient>(fake);
final client = getIt<ApiClient>();
await client.fetch();
await client.fetch();
expect(fake.fetchCallCount, 2);
```

适合：测试业务逻辑是否正确调用了依赖。

### 5.4 模式 D：`environment='test'` 跳过 dev/prod

```dart
await getIt.reset();
await configureDependencies(environment: 'test');
expect(getIt.isRegistered<ApiClient>(), isFalse);
// 测试需要时手工 register
getIt.registerSingleton<ApiClient>(FakeApiClient('test-stack'));
```

适合：完整测试栈，所有跨环境服务都手工 wire。后续可在 source 标 `@test` 自动注册 test-only 实现。

## 8. 设计决策

T02.3 实施过程中做出以下决策。

### 8.1 决策一：示例集中放 `lib/core/di/examples/`

- **理由**: 示例不是生产代码，应清晰可识别。集中目录便于阅读时一眼看到「DI 演示」边界，也便于后续按需删除（项目稳定后可整体移除示例目录）
- **替代方案对比**:
  - 散布到各自语义目录（如 `core/network/api_client.dart`）→ 会与 M04 真实 dio 实现冲突；演示与生产代码混淆
  - 全部放 `core/utils/` → 缺乏语义；不方便检索
- **结论**: `lib/core/di/examples/` 作为示例隔离区

### 8.2 决策二：AppInfo 作为 `@lazySingleton` 示例（沿用 T02.1）

- **理由**: T02.1 已落地 AppInfo（lazySingleton）。T02.3 再造一个 lazySingleton 示例毫无新意。在测试 `registration_types_test.dart` 中直接引用 AppInfo 即可
- **代价**: AppInfo 同时承担「真实服务（M15 会替换）」与「示例」两个角色，但语义清晰，无冲突

### 8.3 决策三：测试覆盖 4 种替换模式而非 1 种

- **理由**: 「测试中替换依赖」是模板使用者最容易踩坑的点。仅给一个模式（如 unregister + register）会让用户在不同测试场景下盲目套用。给 4 个标好适用场景的模式，开发者按需挑选
- **代价**: 测试文件 70+ 行，比单一模式长。但作为示例代码，可读性优于行数
